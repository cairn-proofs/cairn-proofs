# Requirements Document

## Introduction

This change retires the bespoke "wave-based" change-implementation model. It replaces the orchestration layer around that model with a saved Kiro workflow recipe in the shape of Kiro's bundled `feature-pipeline` recipe: one implement step, a bounded review-loop gate, and a full gate. Implementation parallelism stays native to the harness. When a user wants parallel implementation, Kiro generates a run-specific workflow from the change's `tasks.md`. The repository adds no scheduling machinery for it.

The wave model was hand-rolled orchestration. It parsed a Task Dependency Graph from `tasks.md`. It dispatched file-disjoint waves to implementer sub-agents. It tracked state through `openspec/tools/wave_ledger.py`. Earlier harness versions forced this design, because they lacked nested sub-agents and native DAG and loop primitives. The current Claude Code harness allows three levels of agent nesting by default. The current Kiro harness (Kiro 1.4.62 / CLI engine V3) supplies native DAG and loop primitives through workflows.

**Why this change retires the wave model (the evidence the Superseding_ADR must carry).** The hand-rolled layer cost more than it returned:

- **Full-suite re-runs scaled with wave count.** `pyproject.toml` sets `addopts = -n auto`, so a bare `pytest` runs the whole repo. Each wave implementer and the simplify re-confirm ran tests. The full suite therefore ran about W+ times per change. This wasted tokens, because each run's output lands in a sub-agent's context, and it got worse as the suite grew. ADR-0007 records this cost. ADR-0007 depends on the file-disjoint wave invariant to make scoped runs safe. This change removes that invariant.
- **A re-injection contradiction.** `openspec instructions` ships the schema `apply` and `tasks` bytes verbatim to every harness. Kiro sessions therefore received Claude-rooted mechanics — an `Agent` tool, `SendMessage`-resume, and a cohort barrier — that do not map to Kiro primitives. The orchestrator overrode them on every apply. ADR-0016 records this leak and the WHAT/HOW/Surfaces split that contains it.
- **Fragile state tracking.** `wave_ledger.py` kept per-wave status in a per-user ephemeral directory. It carried its own path-safety and atomic-write handling. Native loop primitives make this bespoke infrastructure unnecessary.
- **Planning overhead per change.** Every `tasks.md` carried a `## Task Dependency Graph` JSON block. An author had to build that block and keep it file-disjoint. The orchestrator had to parse it. The payoff was author-planned static implementation parallelism. This change retires the static author-maintained DAG — the portable, parser-free artifact an author had to hand-build and keep correct. It does not retire parallelism.

**The portable surfaces describe a sequential checklist floor. Parallelism belongs to the harness.** The portable surfaces are the OpenSpec `schema.yaml` instructions, the `tasks.md` templates, and `AGENTS.md`. They describe one harness-agnostic contract: a plain ordered checklist that any harness can run top to bottom, prerequisites before dependents. That checklist is the floor, not a cap. The saved Kiro recipe runs the checklist in one `implement` step that follows the Apply_Skill. When a user wants parallel implementation on Kiro, Kiro generates a workflow for the task at hand from the change's `tasks.md`, and Kiro can revise the remaining work between steps. Nothing in the repository schedules that parallelism. There is no plan file, no implementer slot, no planner or reconcile step, no baseline file, and no cross-slot check. A fixed recipe that schedules checklist tasks into parallel implementer slots would rebuild the custom task-management machinery that this change removes. Kiro's documentation states that a `parallel` node gives context isolation and join semantics. It does not promise shorter wall-clock time. The parallelism in the review gate (parallel code-review, security-review, and tester) does not change.

The Superseding_ADR records that implementation parallelism moves from a static author-maintained DAG to the harness's native workflow generation. This is a cleaner supersede story for ADR-0004 and ADR-0005. The Superseding_ADR does not record that this change abandons parallelism.

The migration pursues three top-level goals. First, a genuinely harness-agnostic setup: `AGENTS.md` holds only harness-agnostic workflow content, and each harness keeps its own execution detail in its own configuration (here the Kiro workflow recipe and Kiro steering). Second, removal of the custom wave planning and execution in favor of native harness capabilities. Third, survival of the orchestrator and implementer Kiro custom-agent configs without their prompts, so their load-bearing permissions, tools, and shell guardrails stay intact.

A native Kiro workflow recipe (`.kiro/workflows/opsx-apply.workflow.json`) already scaffolds the target pipeline in the shape of Kiro's bundled `feature-pipeline` recipe. The recipe has one implement step that follows the vendor apply skill. A bounded quality-gate loop follows the implement step: simplify, then parallel code-review plus security-review plus tester, then neutral adjudication, then a bounded fix loop. A single-writer full-gate step follows the loop. The recipe is new. `.kiro/workflows/` is not on `main`. Adding that directory and file to the repository is therefore part of this change. This change makes the rest of the repository coherent with that target: the agent configs, `AGENTS.md`, the OpenSpec schemas and templates, the ledger tooling, and the governing ADRs.

Two facts hold at authoring time and bound the blast radius. ADR number 0021 is free, and only this spec references it. No active change carries a `## Task Dependency Graph` block (nothing under `openspec/changes/` outside `archive/`). Nothing in flight therefore needs migrating, and no in-flight `tasks.md` needs a rewrite.

The `docs/adr/` edits in this change go beyond what ADR-0001 allows today. This change deletes four ADRs, adds one, and amends ADR-0001 once. Requirement 8 gives the reasons. The user has authorized these edits, and the direct edits to `openspec/` schemas and templates, as exceptions for this change only. They are exceptions to ADR immutability and to the usual OpenSpec change-process. They are acceptable because the repository is not yet public. This requirements document is a normal Kiro spec. The authorization covers the content of the requirements, not the format of this document.

## Glossary

- **Wave_Model**: The retired change-implementation model. In it, `tasks.md` carries a `## Task Dependency Graph` JSON block that groups tasks into "waves" keyed on `dependsOn`, the orchestrator dispatches file-disjoint waves to implementer sub-agents, and `openspec/tools/wave_ledger.py` tracks per-wave status. The model includes the "wave", "cohort", and "Task Dependency Graph" (DAG) vocabulary.
- **Aggregate_Gate**: The single post-implementation quality gate. It runs once on the cumulative diff of a change, in this order: `code-simplifier`, then `code-reviewer` plus `security-reviewer` plus `tester` in parallel, then `mise run check`. This change keeps this review philosophy. Only its orchestration mechanics change.
- **Harness_Agnostic**: A property of content or configuration that makes no assumption about which agent harness runs it. Harness-agnostic content names no harness-specific spawn, parallelism, or re-dispatch primitive. It stays coherent under any harness that reads `AGENTS.md`.
- **Orchestrator_Agent**: The Kiro custom agent defined by `.kiro/agents/orchestrator.json`. It is the main-session agent for the `opsx-*` flows. After this change it keeps its permissions, tools, shell constraints, and sub-agent allow-list, and it loses its bespoke wave-orchestration prompt.
- **Implementer_Agent**: The Kiro custom agent defined by `.kiro/agents/implementer.json`. It is a write-scoped implementation sub-agent, denied git mutations and `mise run check`. After this change it keeps its permissions, tools, and shell constraints, and it loses its bespoke wave prompt.
- **Apply_Skill**: The vendor OpenSpec skill at `.kiro/skills/openspec-apply-change/SKILL.md` (MIT-licensed, not project-owned). It is the authoritative procedure to apply any OpenSpec change. It runs `openspec instructions apply --change <name> --json`, reads the listed context files, and loops the pending tasks. It marks checkboxes and honors the CLI's `blocked` and `all_done` states. It contains no wave vocabulary.
- **Steering**: Kiro steering files. They reach sub-agents, which a root agent's system prompt does not. They are the durable home for Kiro-specific cross-cutting rules that must reach sub-agents, such as the document-authoring and spec-writer delegation policy and the ASD-STE100 rewrite policy.
- **Workflow_Recipe**: The saved native Kiro workflow definition `.kiro/workflows/opsx-apply.workflow.json`. It follows the shape of Kiro's bundled `feature-pipeline` recipe: one `implement` step, then a bounded quality-gate loop, then a `full-gate` step. It is the Kiro-specific realization of the harness-agnostic pipeline. Its step `prompt` fields are inline strings only. They cannot reference a `file://` resource.
- **Superseding_ADR**: A new Architecture Decision Record (ADR-0021). It records why this change retires the wave model. It records that implementation parallelism stays but moves from the retired author-planned static DAG to Runtime_Fanout on Kiro, rather than ending. It is self-contained: it restates every decision from ADR-0004, ADR-0005, ADR-0007, and ADR-0016 that still stands. This change then deletes those four ADRs (Requirement 8).
- **Decision_Mapping_Record**: A table in `design.md`. For every decision in ADR-0004, ADR-0005, ADR-0007, and ADR-0016, it records one disposition: restated in ADR-0021, or dropped because only the Wave_Model needed it. It proves that deleting the four ADRs loses no decision that still stands. Requirement 8 criterion 3 is checked against it.
- **Tc_Gate**: The threat-model reconcile-and-gate step. `openspec/tools/tc.py` performs it (`reconcile` then `gate`) for a change that carries a `threat-model.tc.json`. This migration keeps it unchanged.
- **Apply_Entry_Point**: The single Kiro entry point to apply a change with the full review gate. It is the Workflow_Recipe `opsx-apply` (`.kiro/workflows/opsx-apply.workflow.json`), launched by name through Kiro's workflow launcher (for example `run_workflow` in chat or `/workflow run opsx-apply` in the CLI). No steering alias launches it. The user deleted the former manual alias `.kiro/steering/opsx-apply.md`, which pointed only at the Apply_Skill and so ran the bare task loop with no review gate. A Kiro-generated run-specific workflow (Runtime_Fanout) is not saved in the repository and is not a second Apply_Entry_Point.
- **Verdict_File**: The adjudication output `review-verdict.json`. The adjudication step writes it under the Workflow_Recipe's per-run `run_dir` input. `run_dir` is a per-run artifact directory inside the workspace, under `openspec/workflow-runs/`, which `.gitignore` excludes. The file holds `{"verdict": "APPROVED"}` or `{"verdict": "NEEDS_CHANGES", "findings": …}`. The fix step reads it to learn the findings. It is not the loop's stop condition, and no gate precondition trusts it, because another agent can rewrite a file through the shell. The stop condition and the full-gate precondition read the adjudication step's own captured output (`{{adjudicate.output}}`), which ends with exactly one line `VERDICT: APPROVED` or `VERDICT: NEEDS_CHANGES`. No other agent can edit a step's captured output.
- **Line_Mapping_Record**: A table in `design.md`. For every non-blank, non-heading line of the two retired prompt files, it records one disposition: relocated to `AGENTS.md`, relocated to a Steering file, relocated to the Workflow_Recipe, or dropped. It is the auditable artifact that proves this change lost no content. Requirement 3.7 is checked against it.
- **Sequential_Implementation**: The harness-agnostic implementation *floor*. It is a plain ordered checklist, grouped by `##` heading and ordered so each task's prerequisites precede it. Any harness can run it top to bottom through the Apply_Skill, which loops tasks one at a time. It is the contract the portable surfaces describe (the OpenSpec schemas, the `tasks.md` templates, and `AGENTS.md`). It is a floor, not a cap: it is the minimum behavior every harness supports, and it permits a harness to parallelize file-disjoint tasks on its own surface. A harness with no concurrency support runs it exactly top to bottom. The saved Workflow_Recipe runs it in one `implement` step. A harness with concurrency support (Kiro, through Runtime_Fanout) may do more.
- **Runtime_Fanout**: Parallel implementation through a Kiro-generated workflow. Nothing in the repository schedules it. When a user wants parallel implementation, Kiro generates a run-specific workflow from the change's `tasks.md`, and Kiro can revise the remaining work between steps. The repository adds no plan file, no implementer slot, no planner or reconcile step, no baseline file, and no cross-slot check for it. There is no static DAG and no ledger.

## Requirements

### Requirement 1: Retire the orchestrator and implementer prompt files (Scope A)

**User Story:** As a repository maintainer, I want this change to remove the bespoke wave-model prompt files and refresh the agent JSON `description` fields, so that no stale wave vocabulary drives sub-agent behavior or auto-selection.

#### Acceptance Criteria

1. WHEN the change completes, THE Harness_Agnostic_Workflow_Migration SHALL leave the file `.kiro/agent-prompts/orchestrator.md` absent from the repository.
2. WHEN the change completes, THE Harness_Agnostic_Workflow_Migration SHALL leave the file `.kiro/agent-prompts/implementer.md` absent from the repository.
3. WHEN the change completes, THE Harness_Agnostic_Workflow_Migration SHALL leave `.kiro/agents/orchestrator.json` with no top-level `"prompt"` key present.
4. WHEN the change completes, THE Harness_Agnostic_Workflow_Migration SHALL leave `.kiro/agents/implementer.json` with no top-level `"prompt"` key present.
5. WHEN the change completes, THE Harness_Agnostic_Workflow_Migration SHALL leave the `"description"` field of `.kiro/agents/orchestrator.json` as a non-empty string of at most 600 characters. THE field SHALL contain none of these forbidden terms, matched case-insensitively as substrings: "wave", "task dependency graph", "cohort", "ledger".
6. WHEN the change completes, THE Harness_Agnostic_Workflow_Migration SHALL leave the `"description"` field of `.kiro/agents/implementer.json` as a non-empty string of at most 600 characters. THE field SHALL contain none of these forbidden terms, matched case-insensitively as substrings: "wave", "task dependency graph", "cohort", "ledger".
7. WHEN the change completes, THE Harness_Agnostic_Workflow_Migration SHALL leave every top-level key of `.kiro/agents/orchestrator.json` other than `"prompt"`, `"description"`, and `"resources"` with a value byte-equal to its pre-change value. THE `"resources"` value SHALL differ from its pre-change value by exactly one removed entry, `file://.kiro/skills/spec-simplifier/references/writing-recommendations.md` (see Requirement 12). Key ordering is unconstrained.
8. WHEN the change completes, THE Harness_Agnostic_Workflow_Migration SHALL leave every top-level key of `.kiro/agents/implementer.json` other than `"prompt"` and `"description"` with a value byte-equal to its pre-change value. The two exceptions are the archive read denial that Requirement 13 criterion 1 adds to `toolsSettings.read.deniedPaths` and to `permissions.rules`, and the dependency-file and `tasks.md` write permissions that Requirement 2 criterion 7 adds. Key ordering is unconstrained.
9. WHEN the change completes, THE Harness_Agnostic_Workflow_Migration SHALL leave both `.kiro/agents/orchestrator.json` and `.kiro/agents/implementer.json` as syntactically valid JSON that parses without error.

### Requirement 2: Preserve agent permission, tool, and shell guardrails (Goal 3, Constraints)

**User Story:** As a repository maintainer, I want this change to keep the load-bearing permissions, tools, and shell constraints in both agent configs intact, so that the implementer stays write-scoped and the orchestrator keeps its scoped spawn and write authority after the prompts are gone.

#### Acceptance Criteria

1. Requirement 1 criterion 8 already covers the Implementer_Agent config's `toolsSettings.write.allowedPaths` and `toolsSettings.write.deniedPaths` sets: it requires every top-level key other than `"prompt"` and `"description"` to stay byte-equal to baseline. This criterion restates the load-bearing reason. The implementer must stay write-scoped to production and test paths, plus the two dependency files and the change `tasks.md` files that criterion 7 adds, and denied `openspec/specs/**` and `.kiro/**` after the prompt is gone.
2. Requirement 1 criterion 8 likewise covers the Implementer_Agent config's `toolsSettings.shell.allowedCommands` and `toolsSettings.shell.deniedCommands` sets. The load-bearing reason restated here: `deniedCommands` still carries the git-mutation patterns (`git commit*`, `git add*`, `git push*`, `git reset*`, `git rebase*`, `git checkout*`, `git restore*`, `git clean*`) and the `mise run check` pattern, so the implementer still cannot commit or run the full gate.
3. THE Implementer_Agent config SHALL retain its `permissions.rules`, `permissions.policies`, `tools`, `allowedTools`, and `toolsSettings` entries byte-identical to the pre-`"prompt"`-removal baseline, including the `permissions.policies` value `["read-only-shell"]`. The two exceptions are the archive read denial that Requirement 13 criterion 1 adds and the dependency-file and `tasks.md` write permissions that criterion 7 adds.
4. THE Orchestrator_Agent config SHALL retain its `permissions.rules` byte-identical to the pre-`"prompt"`-removal baseline, including the `subagent` allow rule whose `match` list enumerates exactly the spawnable specialists `code-reviewer`, `code-simplifier`, `implementer`, `security-reviewer`, `spec-writer`, `tester`, and `threat-model`.
5. THE Orchestrator_Agent config SHALL retain its `toolsSettings.write.allowedPaths`, its `toolsSettings.write.deniedPaths`, and its top-level `shell.allowedCommands` set byte-identical to the pre-`"prompt"`-removal baseline. In `orchestrator.json` the `shell.allowedCommands` set lives at the config root, not under `toolsSettings.shell`. The load-bearing reason: the orchestrator keeps its scoped write authority (`./openspec/**`, `./scripts/**`, `./docs/**`) and its `openspec.*` and `uv run python openspec/tools/.*` shell allowances. Requirement 1 criterion 7 covers this structurally.
6. (Assumption, not a deliverable of this change.) THIS change ASSUMES that when an agent config carries no top-level `"prompt"` key, the Kiro harness applies the engine default system prompt and still loads the agent's declared `resources` and shared steering, so each agent reads `AGENTS.md` through its `resources` entry `file://AGENTS.md`. The change cannot make the harness behave this way. It can only verify the behavior. THEREFORE THE design SHALL include a check step. After the `"prompt"` keys are gone, the check step SHALL confirm that an orchestrator or implementer agent run still receives the default system prompt and can read `AGENTS.md`. THE design SHALL treat a failure of this assumption as a blocking finding, not a silent regression.
7. THE Implementer_Agent config SHALL permit file writes to the repository-root `pyproject.toml`, the repository-root `uv.lock`, and `openspec/changes/*/tasks.md`, in `toolsSettings.write.allowedPaths` and in the matching `fs_write` allow rule in `permissions.rules`, and SHALL add no other new write path. The implement step can perform a task that adds a dependency, and such a task writes `pyproject.toml` and `uv.lock`. The implement step follows the Apply_Skill, which marks task checkboxes in the change's `tasks.md`. These permissions let the `implementer` complete such tasks.

### Requirement 3: Relocate retained content by type with nothing lost (Scope B)

**User Story:** As a repository maintainer, I want this change to relocate every still-relevant instruction from the retired prompts to the correct layer by type, so that durable guidance survives prompt removal and reaches the contexts that need it.

This content is the Aggregate_Gate pipeline shape, the test discipline, the one-way dependency direction, the secure-by-default patterns, the read-existing-patterns-first discipline, the no-history-lessons rule, and the Tc_Gate reference.
2. THE Harness_Agnostic_Workflow_Migration SHALL place Kiro-specific cross-cutting rules that must reach sub-agents in Steering files. These rules include the document-authoring and spec-writer delegation policy. They also include the rule that the session loads the ASD-STE100 skill to rewrite a document that already exists.
3. THE Harness_Agnostic_Workflow_Migration SHALL place orchestration mechanics in the Kiro Workflow_Recipe.
4. IF content from a retired prompt is already present in `AGENTS.md` or Steering, or an agent JSON config already enforces it, THEN THE Harness_Agnostic_Workflow_Migration SHALL drop that content rather than duplicate it.
5. IF content from a retired prompt describes only the Wave_Model, THEN THE Harness_Agnostic_Workflow_Migration SHALL drop that content.
6. THE Harness_Agnostic_Workflow_Migration SHALL relocate the document-authoring and delegation policy to a Steering file, not to `AGENTS.md` or a step prompt. Steering reaches sub-agents, and the Workflow_Recipe step `prompt` accepts an inline string only. THE Harness_Agnostic_Workflow_Migration SHALL phrase the spec-writer delegation policy and the ASD-STE100 rewrite policy in that Steering file without naming a specific harness, so that it can later move verbatim into `AGENTS.md` once a second harness also has a spec-writer agent. The policy lives in Kiro Steering now only because, at authoring time, only Kiro has a spec-writer agent and only Steering reaches sub-agents. Requirement 10 criterion 7 covers that eventual move to `AGENTS.md`.
7. WHEN the change completes, THE Harness_Agnostic_Workflow_Migration SHALL map every non-blank, non-heading line of `.kiro/agent-prompts/orchestrator.md` and `.kiro/agent-prompts/implementer.md` to exactly one recorded outcome: relocated to `AGENTS.md`, relocated to a Steering file, relocated to the Workflow_Recipe, or dropped per criterion 4 or criterion 5. No line SHALL be left unmapped, and no line SHALL map to more than one outcome. THE Line_Mapping_Record table in `design.md` SHALL be the record of this mapping. Criterion 7 is checked against that table.

### Requirement 4: Rewrite the AGENTS.md Code-change workflow section (Scope C)

**User Story:** As a contributor or agent session reading `AGENTS.md`, I want the Code-change workflow described as a linear aggregate-gate pipeline without wave vocabulary, so that the shared operating manual reflects the native model.

#### Acceptance Criteria

1. THE `AGENTS.md` Code-change workflow section SHALL describe the pipeline as four ordered phases: spec gate, then implement, then the single Aggregate_Gate, then commit. THE section SHALL describe the Aggregate_Gate as running once on the cumulative diff, in the order `code-simplifier`, then `code-reviewer` plus `security-reviewer` plus `tester` in parallel, then `mise run check`.
2. THE `AGENTS.md` Code-change workflow section SHALL keep the Tc_Gate reference. THE reference SHALL describe the `tc.py` reconcile-then-gate step for a change that carries a `threat-model.tc.json`.
3. WHEN the Harness_Agnostic_Workflow_Migration completes, THE `AGENTS.md` Code-change workflow section SHALL contain no occurrence of the terms "wave", "Task Dependency Graph", "cohort", or "ledger".
4. THE Harness_Agnostic_Workflow_Migration SHALL remove the "wave-status ledger" bullet from `AGENTS.md`.
5. THE rewritten `AGENTS.md` Code-change workflow section SHALL name no Kiro-specific spawn, parallelism, or re-dispatch primitive, so that the section stays Harness_Agnostic.
6. WHEN a harness other than Kiro reads the rewritten `AGENTS.md`, THE content SHALL describe a workflow that is coherent and executable without any Kiro Workflow_Recipe feature.
7. WHEN the Harness_Agnostic_Workflow_Migration completes, THE `AGENTS.md` wave-rationale pointers SHALL reference only the Superseding_ADR. No pointer SHALL reference ADR-0004 or ADR-0005 as the wave rationale.
8. THE `AGENTS.md` Code-change workflow section SHALL state, in harness-neutral terms, that an implementation role carries out the implement phase and that this role is distinct from the session that runs the commit and the full gate. The actor that writes code does not also run the final single-writer gate. THE section SHALL name neither harness nor any harness-specific spawn primitive. On Kiro the implementer agent's write and shell scoping enforces this separation. `AGENTS.md` states the principle so that a harness without that enforcement still follows it.
9. THE `AGENTS.md` Code-change workflow section SHALL describe implementation as the ordered checklist floor (Sequential_Implementation) and SHALL name no harness-specific parallel-dispatch primitive, so that the section stays Harness_Agnostic. THE section SHALL NOT forbid or preclude a harness from parallelizing file-disjoint tasks on its own surface. THE section SHOULD note that a harness MAY use its own concurrency where tasks are file-disjoint, and that a harness without concurrency support runs the checklist top to bottom.
10. THE rewritten `AGENTS.md` content SHALL stay in plain operating-manual prose. THE content SHALL NOT adopt OpenSpec or EARS authoring conventions: it SHALL use no RFC-2119 `SHALL`/`MUST` requirement phrasing, no `#### Scenario:` blocks, and no Capitalized_Underscore glossary-term style. Those conventions belong inside `openspec/` and SHALL NOT leak into `AGENTS.md`.
11. THE `AGENTS.md` Code-change workflow section SHALL state that a harness without delegation runs the implement phase in a separate session from the session that runs the full gate and the commit.
12. THE `AGENTS.md` Code-change workflow section SHALL state that a harness without concurrency runs `code-reviewer`, `security-reviewer`, and `tester` one after another.

### Requirement 6: Refactor the cairn and bugfix OpenSpec schemas (Scope E)

**User Story:** As a contributor generating task lists, I want the `tasks` and `apply` instructions in both schemas rewritten to a plain ordered checklist and an implement-then-aggregate-gate flow, so that generated tasks carry no wave packaging rules and no DAG.

#### Acceptance Criteria

1. THE Harness_Agnostic_Workflow_Migration SHALL rewrite the `tasks` artifact instruction in `openspec/schemas/cairn/schema.yaml` to specify a plain checklist grouped by `##` heading and ordered so that each task's prerequisites precede it. THE instruction SHALL contain no occurrence of the Wave_Model vocabulary (wave, cohort, Task Dependency Graph, DAG, ledger).
2. THE Harness_Agnostic_Workflow_Migration SHALL rewrite the `tasks` artifact instruction in `openspec/schemas/bugfix/schema.yaml` to specify a plain checklist grouped by `##` heading and ordered so that each task's prerequisites precede it. THE instruction SHALL contain no occurrence of the Wave_Model vocabulary (wave, cohort, Task Dependency Graph, DAG, ledger).
3. THE rewritten bugfix `tasks` instruction SHALL order the checklist as RED reproduction tests first, then the fix, then regression guards.
4. THE Harness_Agnostic_Workflow_Migration SHALL rewrite the `apply` instruction in both the cairn and bugfix schemas to specify implementing the checklist and then running the Aggregate_Gate, with no wave-orchestration mechanics.
5. THE Harness_Agnostic_Workflow_Migration SHALL keep the Tc_Gate (`tc.py reconcile` then `gate`) block in both the cairn schema's threat-model instruction and its apply instruction.
6. THE Harness_Agnostic_Workflow_Migration SHALL remove the `## Task Dependency Graph` JSON block and all Wave_Model prose from `openspec/schemas/cairn/templates/tasks.md`.
7. THE Harness_Agnostic_Workflow_Migration SHALL remove the `## Task Dependency Graph` JSON block and all Wave_Model prose from `openspec/schemas/bugfix/templates/tasks.md`.
8. THE rewritten schema instructions SHALL name no Kiro-specific spawn, parallelism, or re-dispatch primitive, so that they stay Harness_Agnostic.
9. WHEN `openspec schema validate cairn` and `openspec schema validate bugfix` run after the rewrite, EACH command SHALL exit with status 0. Spec-corpus validation strictness is set in `mise.toml`, as ADR-0022 records.
10. THE `apply` instruction in both the cairn and bugfix schemas SHALL tell the harness that runs it to use its own concurrency strengths. THE instruction SHALL state, in harness-neutral terms, that the harness MAY run checklist tasks in parallel when the tasks are file-disjoint and every prerequisite of each task is complete. THE instruction SHALL state that a harness without concurrency support runs the checklist top to bottom. THE instruction SHALL state that a task never starts before its prerequisites complete.
